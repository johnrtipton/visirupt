# Receiver protocol and legacy test evidence

Use the [current automation guide](../../docs/automation.md) for explicit deployment and transfer. The pipeline supplies a private exact-build manifest, normal own-team signing and a durable writer identity. Standalone legacy probe commands have been removed; the dated evidence below describes the earlier implementation and is not acceptance of the new ownership protocol.

This first receiver transfers original data to Application Support/GameData and checks each chunk before saving its offset. It verifies stored chunks after restart and the original whole-file SHA256 before marking a file complete. Mac tests cover interruption recovery, invalid chunks/offsets, path traversal, symlinks and corrupted committed data. Physical acceptance passed on M2 Vision Pro: a two-MiB fixture retained its first-MiB checkpoint across a real app restart, completed with the original SHA256, matched bytes retrieved back to the Mac, and survived a normal app update. That early probe did not establish full gameplay. Later human-confirmed native2D gameplay is summarized in the repository README; new automation/device acceptance is tracked separately.

The signed receiver bundle is local.games.cyberpunk.assetreceiver. Future native game host updates must preserve this bundle identifier/data container to retain the assets; uninstalling the app would lose its data. Game code is not part of this receiver yet. The original engine's bundle Data path must be mapped to the actual staged asset root before original startup can use these files.

Use make test and make build from this directory. The host transfer.py uses only the Python standard library and Apple's devicectl file-copy transport, rather than adding a network server or depending on expendable URLSession temporary files. It sends at most256MiB per packet; a failed packet may be resent, while saved verified offsets are retained. Source assets are read only. Native receiver receipts, not host guesses, determine the next offset. Keep the receiver window active for processing; interruption or app suspension may delay acknowledgments, but committed chunks persist.


A separate incompatibility/corruption rejection is reported explicitly; the transfer never silently deletes verified files or returns fake success. Inbox packets and checkpoints live in this app's private container. Local progress/receipts/logs live in the explicitly selected private workspace.

The corrected background callback waits for serial checkpoint processing, and the second download/hash/commit completed with the headset off. Batch scheduling now reads Documents/background-transfer-plan.json, prequeues the original remaining256MiB-or-smaller chunks in a public backgroundURLSession, and preserves request identifiers across app restarts. Native BackgroundReceipts contain per-job accepted/rejected state. Out-of-order completed downloads remain staged until their saved offset can be accepted. Rejected bytes are retained for diagnosis, never acknowledged as verified. The native free-space check conservatively requires room for twice the planned remaining bytes plus512MiB before initially scheduling the batch. Do not run the older transfer.py writer concurrently.

The Mac background_transfer.py prepares chunk hashes from the read-only original source and a copy of the device's .checkpoints directory; it refuses to replace an existing plan. That plan contains a bearer token and must remain private. The server binds only the Mac's current Wi-Fi IP and serves only listed UUID-addressed ranges. It supports authenticated open-ended Range retries and logs identifiers/counts without tokens. make background-test verifies planning rejection/resumption cases; make background-serve restarts the same server and same plan after a Mac interruption. Leave the Mac awake and on the same network. The OS still controls background scheduling; a failed transfer can require app reopening/rescheduling, and full84GiBbatch operation is not yet confirmed. Never uninstall the receiver.
